# Part 1: Why Test in a Browser?

## 1. Selenium and Capybara
- Testing the app the way a user does

## 2. Where We Are
- Assignment 3: a multi-page Rails app with models, validations, search
- Assignment 4: turn it into a SPA
  - React, Vue, HTMX, or Turbo: your choice
  - No Node server: HTMX/Turbo use importmap; React/Vue build with npm into Rails
- The model and controller tests from Assignment 3 still pass
- But do they tell you the SPA *works*?

## 3. What Our Tests Can See So Far
- Model tests: validations, associations
- Controller/integration tests: status codes, redirects, HTML returned
- None of them run JavaScript
- None of them click anything

## 4. What They Can't See
- A button with no handler
- An `hx-post` to the wrong URL
- A React component that never re-renders
- An error message that's returned by the server but never shown
- All of these pass a controller test

## 5. The Testing Pyramid
- Many unit tests: fast, focused
- Fewer integration tests
- A few end-to-end (system) tests: slow, but the only ones that use a real browser
- Martin Fowler / Mike Cohn
- Don't turn the pyramid upside down

## 6. Testing Words
- End-to-end (E2E) test
- Acceptance test
- Browser test
- Rails calls them *system tests*
- Mostly the same idea: drive a real browser from code

# Part 2: A Little History

## 7. Selenium: 2004
- Jason Huggins, ThoughtWorks, Chicago
- Was testing an internal time-and-expense app
- Wrote a JavaScript library that drove the page: *JavaScriptTestRunner*
- Ran inside the browser, so it hit the same-origin policy

## 8. The Name
- The main commercial competitor was Mercury Interactive
- Huggins joked in an email that selenium supplements cure mercury poisoning
- The name stuck

## 9. Selenium RC
- Remote Control: a proxy server that injects the JavaScript
- Got around same-origin
- Tests could be written in Java, Python, Ruby, ...
- Slow and fragile; JavaScript in a sandbox can only do so much

## 10. WebDriver: 2006
- Simon Stewart, then at Google
- Drive the browser *from outside*, using each browser's native automation hooks
- No injected JavaScript
- 2009: Selenium + WebDriver merge → Selenium 2

## 11. A Standard
- 2018: W3C WebDriver becomes a Recommendation
- Browser vendors ship their own drivers
  - chromedriver, geckodriver (Firefox), safaridriver
- 2021: Selenium 4 speaks the W3C protocol natively
- WebDriver BiDi: two-way, event-based successor, in progress

## 12. Selenium Manager
- Used to be: download chromedriver, match versions, fix your PATH, repeat
- Selenium 4.6 (2022) adds Selenium Manager
- Finds or downloads the right driver for you
- That's why our demo needs no driver setup

## 13. Capybara: 2009
- Jonas Nicklas
- Replaced *Webrat*, the earlier Ruby tool
- Capybara: the world's largest rodent: a bigger rat
- One DSL, many drivers
- Write `click_on "Save"`, not WebDriver calls

## 14. Rails System Tests
- Rails 5.1 (2017): `ActionDispatch::SystemTestCase`
- Capybara + Selenium, wired up for you
- Screenshots on failure
- Rails 8.1: no longer generated by default
  - DHH: slow and brittle, so keep only a few
  - `rails new` still adds the gems; `--minimal` leaves them out

# Part 3: How It Fits Together

## 15. The Pieces
```
your test  ──Capybara DSL──▶  Capybara
Capybara   ──driver API───▶  selenium-webdriver (gem)
gem        ──W3C WebDriver (HTTP/JSON)──▶  chromedriver
chromedriver ──▶  Chrome (headless)
Chrome     ──HTTP──▶  Puma, started by Capybara, running your app
```

## 16. Two Processes, Three Threads
- Chrome is a separate *process*
- Capybara starts Puma *inside the test process*, on a random port
  - Your test runs on one thread
  - Puma serves requests on others
- So the test and the app run concurrently

## 17. Thread Safety and the Database
- Tests wrap each test in a transaction and roll it back
- Puma's threads must see the test's fixtures
- Rails 5.1+ shares one DB connection across test and server threads
- Consequences:
  - Don't write to the DB from the test while the browser is mid-request
  - Use the UI or fixtures, not `Item.create` halfway through a test

## 18. Drivers
| Driver | JavaScript? | Speed | Use for |
|---|---|---|---|
| `:rack_test` | No | Fast | Plain HTML forms |
| `:selenium` + `:chrome` | Yes | Slow | Watching it run |
| `:selenium` + `:headless_chrome` | Yes | Medium | CI, everyday |
| `:cuprite` (gem) | Yes | Faster | Chrome DevTools Protocol, no WebDriver |

## 19. rack_test
- No browser at all
- Capybara calls your Rack app directly
- Ignores every `hx-*` attribute and every line of JavaScript
- An SPA is almost all JavaScript, so you need a real browser

## 20. Headless
- Full Chrome, no window
- Same engine, same JavaScript
- Required on CI servers (no display)
- Change `headless_chrome` to `chrome` to *watch* a test

# Part 4: The Capybara DSL

## 21. Shape of a System Test
```ruby
require "application_system_test_case"

class ItemsTest < ApplicationSystemTestCase
  test "index lists the items" do
    visit items_url

    assert_selector "h1", text: "Items"
    assert_text "Buy milk"
  end
end
```
- Same Minitest you know, so the same `test "..." do`
- Arrange, act, assert, but through a browser

## 22. Navigating
```ruby
visit items_url
visit item_url(items(:milk))
assert_current_path items_path
```
- `visit` is the only "type a URL" step
- In a SPA, after the first `visit`, the URL may never change
  - `assert_current_path` proves it

## 23. Clicking
```ruby
click_on "Create"        # link or button
click_link "Edit"
click_button "Delete"
```
- Finds by the *visible text* (or id, title, value)
- That's what the user sees, so that's what you test

## 24. Forms
```ruby
fill_in "What", with: "Walk the dog"
fill_in "When", with: Date.new(2026, 11, 6)
select "Fall 2027", from: "Semester"
check "Ada Lovelace"
choose "Spring"
```
- `fill_in` finds the field by its `<label>`
- No label? Capybara can't find it, and neither can a screen reader

## 25. Labels Are Accessibility
- `<label for="item_what">What</label>`
- Capybara finds fields the way assistive technology does
- A hard-to-test form is often an inaccessible form
- React/Vue: you must write the `<label htmlFor=...>` yourself

## 26. Scoping With `within`
```ruby
within "#item_#{items(:milk).id}" do
  click_on "Edit"
  fill_in "What", with: "Buy oat milk"
  click_on "Update"
end
```
- Every row has an "Edit" button
- `within` narrows the search to one element
- `dom_id` gives you predictable ids

## 27. Ambiguity
- Two "Edit" buttons, no `within`:
  - `Capybara::Ambiguous: Ambiguous match, found 2 elements`
- Fixes, best first:
  - `within` a specific element
  - Better labels: "Edit Buy milk"
  - `match: :first` (hides the problem)

## 28. Finding Elements
```ruby
find("#items")                 # exactly one, or error
find("article", text: "Buy milk")
all("article").count           # zero or more
first("article")
```
- `find` waits and raises if it finds none or more than one
- `all` doesn't wait by default, so be careful

## 29. Assertions
```ruby
assert_text "Buy oat milk"
assert_no_text "Buy milk"
assert_selector "article", count: 2
assert_no_selector ".form-errors"
assert_field "What", with: ""
assert_button "Create"
```

## 30. JavaScript Dialogs
```ruby
accept_confirm "Are you sure?" do
  click_on "Delete"
end
```
- `hx-confirm`, `data-turbo-confirm`, and `window.confirm()` all open a native dialog
- WebDriver must answer it, or the test hangs
- Also: `dismiss_confirm`, `accept_alert`, `accept_prompt with:`

# Part 5: Waiting

## 31. The Biggest Idea Today
- `click_on "Create"` returns *immediately*
- The browser sends a request, waits, swaps HTML
- Your next line runs while that's still happening
- This is a race condition between two processes

## 32. Capybara Waits for You
- `assert_text`, `assert_selector`, `find`, `click_on`, ... retry
- Default: up to 2 seconds (`Capybara.default_max_wait_time`)
- Passes as soon as the condition is true
- Fails only after the timeout

## 33. Don't `sleep`
```ruby
click_on "Create"
sleep 1                       # NO
assert_text "Walk the dog"    # this already waits
```
- Too short: flaky
- Too long: slow, every single run
- Waiting for a condition is faster *and* more reliable

## 34. The Negative Trap
```ruby
# WRONG: waits 2s for the text to appear, then refutes
refute page.has_text?("Buy milk")

# RIGHT: waits for the text to disappear
assert_no_text "Buy milk"
```
- Same for `assert_no_selector`
- Always use the `assert_no_` form

## 35. Things Capybara Can't Wait For
```ruby
click_on "Create"
assert_equal 3, Item.count    # checks the DB *now*
```
- The request may not be done yet
- Assert on the page first, then the DB:
```ruby
assert_text "Walk the dog"
assert_equal 3, Item.count
```

## 36. Flaky Tests
- Passes, fails, passes, with no code change
- Almost always a waiting problem
- Run it several times: `for i in 1 2 3; do bin/rails test:system; done`
- Never "fix" it with a retry loop or `sleep`

## 54. The Server Did Its Job
```ruby
render partial: "items/form", locals: { item: @item },
       status: :unprocessable_entity
```
- Returns 422 and the form with the errors
- A controller test checks status 422 and the HTML, and **passes**
- htmx 2 does not swap 4xx/5xx responses by default
- The 422 HTML arrives and is thrown away
- Only a test that runs JavaScript can find this

## 55. Fix Part 1: Let htmx Swap a 422
```erb
<%# app/views/layouts/application.html.erb, in <head> (one line in the file) %>
<meta name="htmx-config" content='{"responseHandling":[
  {"code":"204","swap":false},
  {"code":"[23]..","swap":true},
  {"code":"422","swap":true},
  {"code":"[45]..","swap":false,"error":true}]}'>
```
- Added by HTMX4Rails' `config/initializers/htmx_setup.rb`
- Put the line back: green again

## 56. Fix Part 2: Swap It in the Right Place
```ruby
# ItemsController#create: the button says hx-target="#items",
# so the errors would land in the list
if request.headers["HX-Request"]
  response.headers["HX-Retarget"] = "#item_form"
  response.headers["HX-Reswap"] = "innerHTML"
  return render partial: "items/form", locals: { item: @item },
                status: :unprocessable_entity, layout: false
end
```
- `#update` does the same, targeting `"#" + helpers.dom_id(@item)`
- `dom_id` is a view helper; in a controller it's `helpers.dom_id`
  - A system test found that bug, too

# Part 7: Your SPA

## 58. Any Front End, Same Tests
- Capybara doesn't care what made the HTML
- `fill_in "What"` works on ERB, JSX, or a Vue template
- The demo tests should pass unchanged after you switch front ends
- That's the point: test behavior, not implementation

## 59. Rails Must Serve the Front End
- Capybara's Puma serves your Rails app, and only that: no Node server, no dev server
- **HTMX/Turbo**: importmap, no Node at all
  - `bin/importmap pin htmx.org`; Turbo is already pinned by `rails new`
- **React**: `jsbundling-rails` with esbuild (`rails new app -j esbuild`)
  - npm builds `app/assets/builds/`; `bin/rails test:system` rebuilds it first
- **Vue**: `vite_rails` for `.vue` files
  - `autoBuild` in `config/vite.json` builds for tests; the Vite dev server is optional

## 60. Per-Framework Notes
- **HTMX**: 4xx responses aren't swapped (see "The Server Did Its Job"); `hx-confirm` → `accept_confirm`
- **Turbo**: `data-turbo-confirm` → `accept_confirm`; Turbo Streams update the page async, so assert on text
- **React/Vue**: fetch + re-render is async, so assert on text; wire up `<label htmlFor>`; send the CSRF token in `fetch`

## 61. Selectors That Last
- Best: what the user sees: labels, button text
- Next: `dom_id` ids (`#item_42`)
- Next: `data-testid="item-row"`: `find("[data-testid=item-row]")`
- Avoid: `div > div:nth-child(3) span`, CSS classes for styling (Tailwind!)

# Part 8: Tabs

## 62. Three Tabs
- Assignment 4: Courses, Sections, Students
- As simple as a table of links at the top
- Clicking a tab shows that tab's records
- And it's still a SPA: no full page loads

## 63. What Should a Tab Do?
- Show which tab is selected
- Show only that tab's records
- Change the URL, so Reload and bookmarks work
- Let the Back button go to the previous tab
- Never reload the whole page
- Every bullet is a test

## 64. Tabs in HTMX
```erb
<%# app/views/shared/_tabs.html.erb %>
<nav class="tabs" aria-label="Sections of the app"
     hx-boost="true" data-turbo="false">
  <table>
    <tr>
      <% { "courses" => "Courses", "sections" => "Sections",
           "students" => "Students" }.each do |tab, label| %>
        <td>
          <%= link_to label, { controller: tab, action: "index" },
                aria: { current: (controller_name == tab ? "page" : nil) } %>
        </td>
      <% end %>
    </tr>
  </table>
</nav>
```

## 65. hx-boost
- Turns ordinary links into htmx requests
- Fetches the page, swaps the `<body>`, pushes the URL
- Links still work with JavaScript off
- `aria-current="page"` tells screen readers, *and our tests*, which tab is selected

## 66. hx-boost and Turbo Drive
- Turbo Drive does the same thing, and `rails new` turns it on
- Without `data-turbo="false"`, *both* handle every tab click:
```
Started GET "/students"
Processing by StudentsController#index as */*     ← htmx
Started GET "/students"
Processing by StudentsController#index as HTML    ← Turbo
```
- Every tab test still passed!
- Tests check what the user sees; read `log/test.log` for what the server does
- Pick one: `data-turbo="false"` for HTMX, or drop `hx-boost` for Turbo

## 67. The Layout
```erb
<body>
  <%= render "shared/tabs" %>
  <main>
    <%= yield %>
  </main>
</body>
```
```ruby
# config/routes.rb
root "courses#index"
```

## 68. Fixtures for Three Tabs
```yaml
# courses.yml          # sections.yml        # students.yml
cs3710:                first:                ada:
  name: CS3710           number: 1             first_name: Ada
                                               last_name: Lovelace
```
- One record per tab, each with text that appears on only one tab

## 69. Tab Test 1: A Tab Starts Selected
```ruby
test "the first tab is selected on the home page" do
  visit root_url

  within "nav.tabs" do
    assert_selector "a[aria-current='page']", text: "Courses"
  end
  assert_text "CS3710"
end
```

## 70. Red: A Real Bug
```
expected to find css "a[aria-current='page']" within
#<Capybara::Node::Element tag="nav"> but there were no matches
```
- My first version used `current_page?(courses_path)`
- The home page is `/`, not `/courses`, so no tab was selected
- Fix: choose by `controller_name`
  - Also keeps "Students" selected on `/students/3/edit`

## 71. Tab Test 2: Clicking a Tab
```ruby
test "clicking a tab shows that tab's records" do
  visit root_url

  within("nav.tabs") { click_on "Students" }

  assert_selector "h1", text: "Students"
  assert_text "Lovelace"
  assert_no_text "CS3710"
  assert_current_path students_path
end
```
- `assert_no_text` proves the *old* tab is gone

## 72. The Tab Label Trap
```ruby
click_on "Students"
assert_text "Students"   # always passes: the tab itself says "Students"!
```
- The nav is on every page
- Assert on something only the new tab has: its `h1`, its records
- Or scope it: `within("main") { assert_text "Students" }`
- `click_on "Sections"` may be ambiguous too: the Sections tab or a "Sections" link on a course? Use `within("nav.tabs")`

## 73. Tab Test 3: Only One Selected
```ruby
test "only the clicked tab is selected" do
  visit root_url

  within("nav.tabs") { click_on "Sections" }

  within "nav.tabs" do
    assert_selector "a[aria-current='page']", count: 1
    assert_selector "a[aria-current='page']", text: "Sections"
  end
end
```

## 74. Tab Test 4: Prove It's a SPA
```ruby
test "switching tabs does not reload the page" do
  visit root_url
  # A full page load would wipe out this JavaScript variable
  execute_script "window.stillHere = true"

  within("nav.tabs") { click_on "Students" }
  assert_selector "h1", text: "Students"
  within("nav.tabs") { click_on "Sections" }
  assert_selector "h1", text: "Sections"

  assert_equal true, evaluate_script("window.stillHere")
end
```

## 75. Does That Test Work?
- Remove `hx-boost="true"` and run it:
```
Failure:
TabsTest#test_switching_tabs_does_not_reload_the_page:
Expected: true
  Actual: nil
```
- Every other tab test still passes: plain links *look* the same
- Watch a test fail at least once, or you don't know it tests anything

## 76. Tab Test 5: The Back Button
```ruby
test "the Back button returns to the previous tab" do
  visit root_url
  within("nav.tabs") { click_on "Students" }
  assert_selector "h1", text: "Students"

  go_back

  assert_selector "h1", text: "Courses"
  assert_current_path root_path
end
```
- Wait for the click to finish *before* `go_back`, or you race the browser

## 77. Tabs in React and Vue
- Often just component state: `const [tab, setTab] = useState("courses")`
- Then the URL never changes and Back leaves the app
- Fine for this assignment, but then:
  - Skip `assert_current_path` and `go_back`
  - Use `role="tab"` and `aria-selected="true"`: `assert_selector "[role=tab][aria-selected=true]", text: "Students"`
- With a router (React Router, Vue Router), all five tests apply

## 81. The New Step
```yaml
- name: Run model and controller tests
  run: |
    set -o pipefail
    bundle exec rails test | tee test-output.txt

- name: Run system tests (browser)
  run: |
    set -o pipefail
    bundle exec rails test:system | tee system-test-output.txt
```
- Two steps so the log shows which kind failed
- `pipefail`: without it, `tee` succeeds and hides a failure

## 84. React and Vue in CI
```yaml
- name: Build JavaScript
  if: hashFiles('package.json') != ''
  run: |
    npm ci
    npm run build --if-present
```
- Skipped for HTMX and Turbo apps with no `package.json`
- `npm ci`, not `npm install`: installs exactly what `package-lock.json` says
- Commit `package-lock.json`, or CI can't build
- Node runs once, to build; it never serves a page

## 85. Auditing JavaScript Dependencies
```yaml
- name: Scan npm packages for known vulnerabilities
  if: hashFiles('package-lock.json') != ''
  run: npm audit --audit-level=high

- name: Scan pinned JavaScript for known vulnerabilities
  if: hashFiles('config/importmap.rb') != ''
  run: bundle exec ruby bin/importmap audit
```
- A React app pulls in hundreds of packages, mostly dependencies of dependencies
- OWASP A03:2025 Software Supply Chain Failures
- `npm audit fix`, or `bin/importmap outdated` and re-pin; then rerun your tests

## 86. Before You Push
```bash

```
- CI is a second check, not your first
- A system test that fails only on CI is usually a waiting problem

# Part 10: Security, Debugging, Wrap-Up

## 88. An XSS System Test
```ruby
test "user input is escaped, not run" do
  visit items_url
  within "#item_form" do
    fill_in "What", with: "<script>alert(1)</script>"
    click_on "Create"
  end
  assert_text "<script>alert(1)</script>"
end
```
- A05 Injection (XSS): escaped → you see the text; not escaped → Selenium hits an unexpected alert

## 89. System Tests and OWASP (Top 10:2025)
- A05 Injection: the XSS test on the last slide
- Rails turns CSRF checks *off* in tests, so system tests won't catch a missing token
- A08 Integrity: HTMX4Rails loads htmx from unpkg with no `integrity=` (SRI) hash
  - `bin/importmap pin htmx.org` serves your own copy instead
- A03 Supply chain: `bundle-audit`, `npm audit` (React/Vue), `bin/importmap audit` (HTMX/Turbo)

## 90. Debugging a Failing System Test
- Open `tmp/screenshots/failures_*.png`
- `take_screenshot` anywhere in a test
- Use `using: :chrome` to watch it
- `puts page.html` to see the current DOM
- Pause with `binding.irb` to poke around in the browser

## 91. Summary
- Selenium drives a real browser through the W3C WebDriver protocol
- Capybara gives you a user's vocabulary: `visit`, `fill_in`, `click_on`
- Rails system tests wire them together, but you have to ask for them now
- Capybara waits; never `sleep`; always `assert_no_`
- System tests find bugs that no other test can, like a 422 that never appeared
